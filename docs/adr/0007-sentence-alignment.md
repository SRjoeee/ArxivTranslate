# ADR-0007: Sentence alignment — the design the code cites as §8.6

- Status: accepted (records the design as implemented 2026-09-08 … 2026-09-10; written down 2026-09-13)
- Evidence: `docs/rebuild/INVENTORY.md` §4.6 ("a whole design lives only in code comments"); the 18 code and test sites that cite a DESIGN §8.6 that was never written; `src/providers/alignment.ts`, `src/providers/sentence-markers.ts`, `src/core/sentences/index.ts`, `src/core/pipeline/sentences.ts`, `src/providers/translate-service.ts`, `src/cache/key.ts`, `src/core/renderer/sentences.ts`; issues #105, #137, #145, #148

## Context

The hover highlight (DESIGN §7.7, issue #105) tints the sentence under the pointer and its counterpart on the other side. That needs to know which sentence of the translation corresponds to which sentence of the original, and the pipeline gets it from the engines, never by guessing: matching two finished texts by position was measured first and rejected (`sentence-markers.ts`, module header — over 37 real blocks the sentence counts agreed on 67.6%, but on the blocks with more than one sentence, the ones the highlight exists for, only 8 of 20). The design was built between 2026-09-08 and 2026-09-10 (`53a3853` the contract and Microsoft reporting it; `178c381` … `2d422f5` the splitter; `bf8feb1` the markers; `e0dc759` the cuts decided where the block is known; `7ae65fd` the snap; `b62597a` the peek), and every part of it cites "§8.6" of DESIGN.md, a section that does not exist. This ADR is that section, reconstructed from the code as it stands; DESIGN.md §7.7 keeps what it already says about the highlight itself and is not repeated here.

## Decisions

### 1. What an alignment is, and the one gate it passes

A `SentenceAlignment` is two lists of sentence lengths in **wire-text coordinates** — `source` for the text sent, `target` for the text that came back — entry *i* of each being one sentence pair (`providers/alignment.ts:SentenceAlignment`). It is accepted only if it reconstructs both texts exactly: `verifyAlignment` requires equal, non-empty sentence counts, positive integer lengths, and sums equal to each text's length; anything else returns `undefined`. Counts must match because the highlight pairs sentence *i* with sentence *i* — an engine that merged two source sentences into one target sentence has no pairing to offer, and the honest answer is no highlight (`alignment.ts:verifyAlignment`, with the note that across 60 real blocks Microsoft's counts matched on every one, so the check rejects malformed data rather than a normal case). Total lengths, not per-sentence content, are what it can check: the boundaries are the claim being verified, so the only independent facts are the two strings.

**A dropped alignment costs only the highlight.** The translation is untouched, the block is rendered, and `registerSentences` simply does not register it (`renderer/sentences.ts:registerSentences`); a guessed pairing would put the highlight on the wrong sentence, which is worse than none. That rule is stated at every layer and is the one architectural requirement issue #105 put on the provider layer: `TranslatedSegment.alignment` is present only when the engine could report boundaries **and** they reconstructed both texts, and the pipeline never branches on how it was obtained (`providers/types.ts:TranslatedSegment`).

### 2. One verification, at the service, on both paths

Whichever engine produced it, the alignment is verified once in the service, against the **unmarked** source text: `translate-service.ts:translateItems` compares `outcome.value.alignment` with `item.source` (the raw wire text, since `item.text` may carry markers and its length would not match) and the returned text; the cache-hit path verifies again the same way (`translate-service.ts`, the `hit.alignment` branch), because an old record may carry an alignment that no longer describes the current gate. Microsoft verifies in the provider as well (`microsoft.ts:translateTexts`), which is why the snap below has to be idempotent. The verified alignment is stored with the cache record (`cache/store.ts:CacheRecord.alignment`; its bytes count toward the entry's size) and an old record without the field reads back as "no alignment", needing no invalidation.

### 3. Who reports boundaries, and how the others are made to

Two mechanisms, one contract:

- **Microsoft reports natively.** The endpoint returns `sentLen` (`srcSentLen` / `transSentLen`) measured on the exact strings sent; the provider declares `reportsSentences: true` and the service inserts nothing for it (`microsoft.ts:createMicrosoftProvider`). Measured over 60 real blocks: the partition was complete on all 60 and 96.2% of boundaries landed after sentence punctuation — but only once whitespace was collapsed (#119), which is what made it worth reading at all (`microsoft.ts:translateTexts`).
- **Every other engine gets markers.** The boundaries are put *into* the request and read back out: the source is split (decision 4), a `<x id="N"/>` marker is inserted at each cut, and the sentence lengths on the translation side are read off where the markers landed (`sentence-markers.ts:markSentences` / `unmarkSentences`). `<x id="N"/>` is the void placeholder the `tags` wire format already uses, so nothing new has to survive translation; measured against the live Google endpoint before writing any of it, three markers between four sentences came back as three, placed exactly at the boundaries, while `<s id="N"/>` came back with `</s></s></s>` appended and `<wbr id="N">` was dropped entirely (the module header's table). Marker ids are allocated above every id the block uses, so a marker can never be mistaken for one of the block's own placeholders. `unmarkSentences` returns a partition only if every marker came back exactly once and in order; otherwise `stripMarkers` still removes whatever came back, because a leftover `<x id="N"/>` would reach `validate` as a placeholder the block has no slot for and fail the whole block — trading a missing highlight for a missing translation.

The markers enter and leave at the service layer, not in each provider, because the mechanism is engine-independent — any engine that keeps `tags` qualifies, and one copy per provider would be one bug per provider (`translate-service.ts`, the `markedItem` note). Only the `tags` render path is marked: `markers` has no marker that survives the wire, and `runs` sends fragments of a block that `joinRuns` reassembles without wire offsets, so an alignment there would have nothing to attach to. A segment whose marked text would exceed the engine's per-request character cap is sent unmarked: BatchQueue's cap stops only the merging, an oversized single task goes out all the same, and over the cap is a whole batch failed where no marker is only no highlight (Codex on #137). A one-sentence block gets no marker and a whole-for-whole alignment.

`alignment.ts`'s header also says an LLM "reports them through its structured output schema". **Unverified in the code as of 2026-09-13**: no LLM provider (`openai-compat.ts`) reads or returns boundaries; LLM engines take the marker path like Google. The sentence is the intended third mechanism, not an implemented one.

### 4. Where the cuts are chosen, and why the choice is the pipeline's

The splitter (`core/sentences/index.ts:sentenceCuts`) runs on **wire text**, after `serialize`: formulas are already placeholders, so `f(x) = 0.5` cannot be mistaken for a sentence end, and the remaining hazard is abbreviations. It segments a *projection* in which each placeholder becomes whitespace — except a void that opens a sentence, which becomes a word so the boundary stays visible — because `Intl.Segmenter` sees `.` followed by `<` rather than by whitespace at a run-in heading and reports no boundary at all (`sentences/index.ts:project`; `tests/fixtures/arxiv/2312.17527.html` alone has 18 run-in headings). Measured against Microsoft's `srcSentLen` over 60 real blocks: 98.4% precision and 91.7% recall, and **100% precision once bibliography blocks are excluded** — both spurious cuts there were journal abbreviations. What remains is under-splitting (13 of 146), which widens a highlight to two sentences; over-splitting, which would put a highlight on half a sentence, does not occur. The abbreviation list can only remove cut points, so extending it cannot lower precision (checked offline over all 3 210 fixture blocks).

**The cut points are computed in the pipeline, not in the service** (`core/pipeline/sentences.ts:cutsOf`, carried on `TranslateSegment.cuts`; `pipeline/run.ts:cutsFor`). Choosing them needs the block: `sentenceCuts` takes a `SplitContext` built from the placeholder slots to tell an annotation from a formula — a sentence-final full stop may hide inside a math node, and a `\citet` placeholder is itself the sentence's subject — and its measured precision expressly excludes reference blocks, which callers must not run it on (Codex on #137 pointed out both). None of that is visible in the wire text the service holds, so the service only inserts markers by position. Three consequences pinned in code: reference units (`bibblock`, `bibitem`) are never cut; only footnotes count as annotations, blanked to a space when sentences are cut, while citations keep their own text so a `\citet` subject does not merge two sentences (`rules/latexml.ts:ANNOTATION_SELECTOR`); and **an empty cut list is not the same as none** — `[]` says "one sentence, aligned whole to whole", `undefined` says "not aligned", which is where references and the non-`tags` paths fall.

### 5. The cuts enter the cache key

`CacheIdentity.cuts` is part of the key (`cache/key.ts:buildCacheKey`, serialised as `null` when absent so keys without cuts are as before). Two blocks can serialise to the same wire text with different slot semantics, so `cutsOf` gives them different cut points; without the cuts in the key the second block would hit the first's entry, mismatched alignment included, and `verifyAlignment` — which checks counts and total lengths only — could not catch it (Codex on #137).

`CACHE_KEY_VERSION` went 5 → 6 with the markers (#105, commit `e0dc759`). The request sent changed: the same text now goes out with `<x id="N"/>` boundary markers, so an old entry no longer describes the same request. Unbumped, every paper translated within the 30-day TTL would have hit the old entries without alignment and the highlight would have stayed dark on those pages (Codex on #137; `cache/key.ts`, the version history).

### 6. Snapping a boundary that missed its sentence end

Engines report where they think their own sentences end and are occasionally a character or two out: Microsoft returned `…对话式工作流程。这|种新兴的…` on `arxiv.org/html/2509.10652v3`, leaving the first character of one sentence tinted as part of the one before (user report 2026-09-09, reproduced live). The partition is still exact, so nothing downstream rejects it; only the reader sees it. `verifyAlignment` therefore ends with `snapAlignment` (`alignment.ts`, commit `7ae65fd`), which runs after the checks — it only ever moves a boundary inside a text already verified, so the result is exact by construction — and moves nothing that is already right: a boundary already after sentence-final punctuation is left alone, one with no such punctuation within `SNAP_WINDOW` (3 characters) is left alone (an author list has nothing to snap to), and a candidate is refused when it is a period with a lower-case letter or a digit after it (`Vol. 2`, `3.5`), an abbreviation's period that does not end sentences, or would leave a neighbour with nothing visible. A boundary equally near a sentence end on both sides is undecidable, and one undecidable boundary leaves the whole side as reported; the candidates are verified all-or-nothing against their snapshot, because backing off one by one would make the result depend on iteration order (Codex on #145). The walk to the end of a run of terminators happens whichever way the candidate was found, or the snap would not be idempotent across the three verifications (provider, service, cache hit). Measured over 483 real alignments from both engines — 3 532 boundaries, five papers — **2 moved, both onto the sentence end they had missed, 0 correct boundaries touched, and no sentence left without visible text** (the count stayed at its baseline of 36).

### 7. How the renderer consumes it

`registerSentences` captures the three things that exist together only at the instant of rendering — the source side's wire spans from `serialize`, the translation side's from `rehydrate`, and the verified boundaries — in a module-level `WeakMap` keyed by the **translation** node, so the record dies with what it describes; the original holds only a `WeakRef` (`renderer/sentences.ts`, the two-map note; keying by the original would retain one detached subtree per block for the page's life, Codex on #130). Table cells are registered cell by cell after `renderTable`; side mode's split-figure copies are registered too and the first *rendered* one answers, so the highlight follows the copy while it exists (#139); a round without an alignment voids every record of that source, copies included, since a copy is itself a key (#148). A second consumer is the leading-label restore: `protector/label.ts:endsSentences` uses the engine's first boundary as evidence that a label was kept as its own sentence, and a label without a reported alignment is left alone.

## Consequences

- Coverage follows the engines: Microsoft and any `tags`-capable engine through markers (Google, the LLMs, the Chrome built-in translator); the `markers` and `runs` paths, reference blocks and any block whose alignment fails verification have no highlight and no peek. This is by design, and the popup and settings say nothing about it.
- The cache key carries the cuts and the version carries the request shape; a change to the splitter that moves cut points changes keys on its own, a change to the marker syntax needs a version bump.
- The snap is a correction of the engines' reports, bounded to three characters and to punctuation; it is not a second aligner.

## Deliberately not done

- **Paragraph-level pairing for blocks without an alignment** (LLM blocks, the runs path): the peek of §7.7 could fall back to showing the whole original paragraph when the sentence is unknown — "Phase B" of issue #141, left until real use asks for it (the roadmap #155, Phase 0).
- **A second aligner** that guesses from sentence counts or punctuation alone; measured and rejected (decision 1).
- **Reporting boundaries from the LLM prompt schema**: named in `alignment.ts` as a mechanism, not implemented (decision 3).
