# ADR-0001: Rebuild governance

- Status: accepted (owner, 2026-09-12)
- Applies: `docs/rebuild/CHARTER.md`

## Context

Phase 1 of the roadmap (#155) closed with PR #168; the MVP is complete. The owner mandated a systematic rebuild toward the next version (the charter). Several repository conventions written for the MVP push — one module per PR, a fixed tech stack, "DESIGN.md is the single source of truth, change the document before the code" — would constrain the rebuild in ways the charter explicitly rejects (§4, §5). The rebuild needs a stable baseline to measure against (§6) and a record that survives context switches (§7).

## Decisions

1. **Baseline.** `main` after #168 is the MVP baseline, tagged `v0.3.0-mvp`. The name continues the existing internal sequence (`v0.1.0-phase1`, `v0.2.0-phase2` mark the old DESIGN phases of 2026-09-03); `package.json` stays at `0.0.0` — this is an archive mark, not a release. `main` does not move during the rebuild except for owner-requested hotfixes.
2. **Workspace.** The rebuild lives in the worktree `.worktrees/rebuild` on branch `rebuild/v1` (the roadmap calls the Phase 2 outcome V1.0), based on the tagged baseline. Nothing merges into `main` without the owner's explicit request.
3. **`docs/DESIGN.md` is frozen** as the record of the v0.1 implementation: read-only evidence, cited by section, no longer the source of truth. Every rebuild decision is an ADR under `docs/adr/`; progress checkpoints go to `docs/rebuild/PROGRESS.md`. When the rebuild closes, the design document is rewritten from the ADR set (whether as a new DESIGN.md or as `CONTEXT.md` + ADRs is decided then). Factual errors in DESIGN.md that would mislead a reader may be corrected with a dated note; nothing else is edited there.
4. **Conventions retired** from `CLAUDE.md`: one module per branch/PR; the tech stack as fixed and not to be re-chosen; plan mode for modules over 100 lines; the Phase 0 task list (finished; conclusions are in RESEARCH.md).
5. **Conventions kept.** Hard rule 1 (DOM invariants — a product promise, guarded by tests), 5 (`axt-` prefixes — the DOM contract), 6 (cache key carries every version), 7 (secrets never leave WXT storage), GPL source attribution, and the Codex merge gate — now preceded by a local Codex adversarial review before a PR is opened. Hard rules 2 (`ltx_*` selectors only in the rules module) and 3 (two render paths, no provider special-casing in the renderer) stay as defaults; they may be re-evaluated with evidence, since they are themselves instances of "fewer special paths".
6. **External contracts** that get explicit migration or compatibility handling (charter §3): the saved configuration schema in WXT storage (versions and migrations continue); the Native Messaging protocol between the extension and the installed `axt-helper` (compatible, or version-negotiated); the extension's install surface (`helper/install-remote.sh`, manifest path, extension id). The Dexie translation cache is treated as disposable: clearing it costs a re-translation and nothing else, so a schema change may drop it (the owner was told, 2026-09-12). The helper's install directory `~/Library/Application Support/Readarxiv/helper` keeps its spelling although it differs from the repository name: it is written into installed readers' host manifests, readers never see it, and a rename would only orphan the old build directory (owner, 2026-09-12).
7. **Working method.** A PR is one complete, explainable, verifiable design change; cross-module changes update the interface and every caller together. Every PR runs the local Codex adversarial review, then CI and the Codex GitHub review. Agents run in parallel only for read-only work (inventory, multi-angle review, measurement) or for implementation on disjoint file sets; cross-module interface changes are single-threaded.
8. **PR granularity.** The MVP measured its own review cost on 2026-09-08 (nine PRs, 32–845 lines): PRs under 100 lines took at least one Codex run, PRs over 491 lines at least five or six, and each large round carried more comments. The MVP's answer was "one module per PR, and small". The charter's answer is different: a PR is one complete, explainable, verifiable design change, whatever its size, because a coherent change is cheaper to understand than five partial ones — and the review cost is paid down by the local Codex adversarial review before the PR is opened, plus the self-review rules kept in `CLAUDE.md`. Unrelated changes still stay out of a PR.
9. **Ported code.** The MVP policy "port the whole directory, clean up later" produced unused functions and modules that now count as debt (the inventory lists them). From here on only code that is called is kept; when a ported module is touched, its unused parts are removed, and the GPL header and `THIRD_PARTY.md` entry stay for whatever remains.
10. **Public client constants are not secrets.** `src/providers/google-web.ts` carries the API key of Google's own web translator, inherited from KISS Translator and embedded in every copy of that public client. Hard rule 5 ("secrets never enter git") is about our credentials and the reader's; moving this constant to runtime would change nothing about its exposure and is not done (owner, 2026-09-12).

## Consequences

- The next maintainer reads `CLAUDE.md` (short), the charter, and the ADRs — not a 3000-line design document — to learn what is decided and why.
- `RULES_VERSION` / `PROMPT_VERSION` / storage schema versions still bump whenever meaning changes; the cache key rule makes "same text, different translation" safe by construction.
- Old conventions that were evidence-based (measured, tested) survive as tests and ADRs; conventions that were habits do not survive at all.
