## 2026-09-13 — one way to wait for the chain after a save (INVENTORY P4)

- Branch `rebuild/chain-fresh` (PR #182). The popup restarted a page on new settings after polling `axt:provider-status` ten times with a field predicate of its own choosing (`shared/chain.ts`, deleted); the options page's `axt:engine-ready` was the other path. Now `axt:provider-status { fresh: true }` (`background/provider-status.ts`) reads the stored configuration, offers it to the chain holder — the same comparison the storage event makes, so a matching offer starts nothing — and answers from the chain in force once it lands. The race between the save and the storage event (Codex on #157) closes there instead of being outwaited.
- Codex's review on the PR (P2, adopted): a storage event carries no order, so two quick saves could have the first event's value offered after the second save was read and offered, building the older chain on top. Every offer now goes through `createConfigOffers` — the watcher's and `fresh` alike read the store at their turn, one read at a time — and the test models a read as the store at issue time, answered in the worst order (a mutation to unordered offers fails it).
- Tests 1 634 (+4); five mutation checks; gate green by exit code; `pnpm e2e` 72/72.
- INVENTORY §4 rows that no longer hold, checked while choosing this item: S4 (every fatal decision reads `isPermanentErrorKind`), S5 (`REAL_TRANSLATION` in `attrs.ts`, held by `translation-boundary.test.ts`), S9 (no hand-written session guard left) — all closed by ADR-0003 / 0004 / 0006 as side effects. ## 2026-09-13 — `nativeMessaging` optional, one OCR backend seam (ADR-0002 implemented)

- Branch `rebuild/ocr-permission` (PR #179). `optional_permissions: ['nativeMessaging']`, requested from the reader's click in `ui/HelperPermission.tsx` (popup card and settings section); `background/ocr-backend.ts` is the seam (`OcrBackend`, `OcrBackendError`), `createHelperClient` its only implementation; `HelperStatus` is a four-state union.

- Local adversarial review, pass 2: one high finding adopted — the unconditional `tabs.onUpdated` listener is fed by every tab (a ticking title is an event every few seconds) and would have kept the stale worker alive too; `helper-restart.ts` takes it down on every stale answer (`quiesce`), the fresh worker registers it again at start-up; until then a tab that navigates away is not noticed (its queued batches finish or die with the stale worker; the fresh worker starts with no sessions), a closing tab still drops through `onRemoved`.
- Local adversarial review, pass 1: one high finding adopted — the popup's 500 ms provider poll would keep the stale worker alive (and the grant pending) for as long as the popup stayed open on a translating page; `pollsBackground` (popup view model) pauses that half of the loop during `restarting`, the page-status half goes to the content script and stays.
