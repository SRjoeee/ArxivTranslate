## 5. Not understood, or to be verified

1. **`.ltx_note`'s `descend` and the extractor's descent**: only `note` in `PROTECT_RULES` carries `descend: true` (latexml.ts:119); the extractor does not descend into the other protects. But `serialize` clones every protect whole as a void — the footnote body becomes a block and is then cloned whole into the paragraph translation, and `localizeNotes` copies the translation into the copy afterwards. This “clone first, patch later” chain holds only through three modules (extractor / protector / notes) together, and I found no test writing it down as an invariant (`renderer/notes.test.ts` tests the patching, `protector/clone.test.ts:25` tests deleting translations when cloning); whether it stays in the rebuild needs a design-level decision.
2. **`renderTable`'s `rendered` report and `registerCells`** (run.ts:298-304): sentences are registered with the clone cell as target and the source cell as source, but the clone cell has no `data-axt-for`, and `sentenceMapAt` walking up from the clone cell hits the `.axt-t` table first — I did not verify that `recordOf`'s lookup order always lands on the cell when “the table itself is unregistered, the cells are” (`sentences.test.ts:124` tests only the split-figure mirror case).
3. **The real cost of `highlight.ts`'s MutationObserver at the peak of translation** has no number: DESIGN §7.7 gives a frame-cost table for pointermove, not “the observer callback's cost while each batch inserts hundreds of nodes”; 4.5 above can only mark it as sensitive.
4. **The O(N²) of `lazy.ts:144 release()`** comes from reading the code only, not measured on the 880-block fixture; `includes` is fast and the real cost may be under 1 ms.
5. **`data-axt-fit` written on the source table** (table-fit.ts:207-211 writes on both `table` and `translation`) — does it count as the “gaining `data-axt-*`” §7.1 allows? By the wording of CLAUDE.md hard rule 1 yes, by the enumeration of DESIGN §7.1:302 no; which document is the yardstick has to be decided.
6. **`PlaceholderIntegrityError`** (validate.ts:37) is thrown by `rehydrate`, but run.ts `validate`s before every `rehydrate` call, so on the production path the exception should be unreachable; the `try/catch` at `run.ts:204-208` wraps `joinRuns` only. Whether it is pure defence — I found no path that triggers it.
7. **`FIGURE_SELECTORS.picture` and the `picture` of `SKIP_RULES`** (`svg, .ltx_picture`): the text pipeline skips svg whole, the image pipeline takes only `svg.ltx_picture` and demands words — what an inner `svg` nested in `.ltx_picture` (excluded at image/run.ts:106) and a bare `svg` without `.ltx_picture` (taken nowhere) each are, I did not check on the fixtures.
8. **The “move” wording of DESIGN §7.2:325-327** against the code's “copy”: I judged the document stale (Codex #26 and the test `notes.test.ts:109` support it), but that passage says “decided by the owner”; whether a later decision changed “move” back to “copy” without being recorded can only be confirmed from the PR history.
9. **`scripts/fixtures-stats.ts` and `scripts/phase0/td-numeric-calib.ts`** import `UNIT_RULES` / `SKIP_RULES` / `FIGURE_SELECTORS.figure` directly — they are the only consumers of the rule tables outside src; if the rebuild makes the tables non-exported, the two scripts move with them. I did not run them to confirm they still run.
10. **`entrypoints/content/index.ts`** (467 lines) is outside my scope, but it is `core`'s only assembly point: `start()` / `endRun()` / `restorePage()` / `enterSide()` string 13 core entry points together and hold seven handles — `run` / `images` / `modes` / `prep` / `highlight` / `title` / `uninstallAnchors`. The consistency between this layer's state (`progress` / `running` / `current` / `restarted` / `styleFromWatcher` / `resumeRaster`) and core's state (the session singleton, the run's outcome, the image outcome) has no test at all (`tests/entry/` tests only abstract and context-menu); it is the place most worth a baseline first in the rebuild.
