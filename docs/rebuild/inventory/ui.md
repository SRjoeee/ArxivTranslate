## 2. The state model and the message list

### 2.1 What each of the four places holds

**popup** (`usePopupData` in `entrypoints/popup/data.ts`, pure React state, destroyed when the popup closes):
- `page: PageStatus | null` — polls `axt:page-status` every 500ms (`data.ts:74-76`), once more every 500ms while translating (`data.ts:136-143`)
- `provider: ProviderStatus | null` — `axt:provider-status` (`data.ts:81-85`), asking about this session's own chain with `scope` while translating
- `config: Config | null` — `getConfig()` once at mount (`data.ts:95-98`), afterwards echoed locally only after **this page's own** `patchConfig` succeeds (`data.ts:169`), **no `watchConfig` subscription**
- `pack: PackState | null` — looked up once at mount, again after a target-language / service change (`data.ts:86-90`), calling the browser API of `shared/pack.ts` directly, not through the background
- `helper: HelperStatus | null` — `axt:helper-status` at mount (`data.ts:103`), looked up again on the `axt:helper-ready` broadcast (`data.ts:109-116`)
- `platform`, `menu` (its own UI state: which menu is open), `shortcut`, `error`

**options** (`useOptionsData` in `entrypoints/options/data.ts`, React state, resident for the tab's lifetime):
- `config: Config | null` — likewise read once at mount + echoed after its own writes (`data.ts:73-77`, `104-111`), **likewise no `watchConfig` subscription**
- `fallbackReason` — read at mount, cleared after a successful write (“a valid write is itself the repair”, `data.ts:109`)
- `pack: PackState | null` — **a second copy fully independent of the popup's**, looked up once at mount (`data.ts:76`), maintained by `checkPack`/`fetchPack` each, with a `wanted` ref keeping an old request from overwriting a newer one (`data.ts:47-58`)
- `helper: HelperStatus | null` — **a third copy fully independent of the popup's**, `recheck: true` forcing a fresh probe at mount (`data.ts:81`)
- `cache: CacheStats | null` / `cacheError` — read at mount and re-read on the `visibilitychange`/`focus` events (`data.ts:84-91`, reason in section 5)
- `cacheCleared` — the 2-second notice state after clearing

**content script** (`entrypoints/content/index.ts`, closure variables, destroyed on page reload; the core lifecycle state is in the largest file of 1.1):
- `blocks: Block[]` (extracted once, resident in memory), `savedMode` (the preference in the configuration, a placeholder until read back), `modes: ModeController | null` (the mode really in effect and the switching logic)
- `progress: Progress`, `running: PageStatus['running'] | null`, `current` (this session's start snapshot: session id, config, context, renderPath)
- `look: Look` (the appearance, three write points sharing the single `styleFromWatcher` gate, see section 5), `highlight`, `images`, `imageProgress`, `restarted` (keeps a permanent change from being triggered twice by the same chain)

**background** (`entrypoints/background/index.ts`, a Service Worker, rebuilding everything but persistent storage on every wake):
- `active: Promise<{config, transport}> | null` — one engine chain and queue shared by the whole browser (the comment: `the cross-tab quota policy`); inside the `watchConfig` callback `chainConfigChanged` decides between rebuilding and swapping the config in place (`background/index.ts:43-55`)
- `uiLanguage` — used to tell whether the interface language changed, to redraw the context-menu title
- Session routing (`sessions.ts`, not expanded): session id → the chain it is bound to, withdrawn when the tab closes
- The recognition-helper client and waiter (`helper.ts` / `helper-await.ts`, not expanded): the probe result and the deadline of “waiting after copying the install command” — **this is the authoritative source of `until`/`timedOut` in `ui/HelperSetup.tsx`**, and after an unmount / remount the component picks the state up again through `axt:helper-await` (`ui/HelperSetup.tsx:29-35`)

Configuration persistence (`config/storage.ts`, outside this audit's scope but the common source of the four states above) exists once; what the four places read is a snapshot of it at some moment, or a subscription.

### 6.4 i18n

- **Two interface languages**: `zh-CN` (Simplified Chinese, the type's source) and `en` (English, the fallback), defined in the `LOCALES` constant at `src/locales/index.ts:27-30`; the `Widen<T>` type trick (`index.ts:18-22`) forces `en.ts`'s structure to match `zh-CN.ts` exactly — one key fewer or one nesting level more fails to compile — so “a key in zh but not in en” **cannot happen structurally between these two packs** (CI's `pnpm typecheck` stops it first), and this audit therefore concentrated on “defined but unused in the code”.
- **Exact key counts** (by checking `zh-CN.ts`'s object literal by hand, see the method note): `S` (popup copy) **73** leaf keys, `O` (settings-page copy) **150** leaf keys, `REASON` (error reasons) **9**, plus the 2 of `locales/preview.ts`, `PREVIEW_SOURCE`/`PREVIEW_TARGET` (referenced by both packs), **about 234 localisable strings / functions in all**.
- **The zero-hit scan method**: for the “last segment of the name” of all 232 `S`/`O`/`REASON` leaf keys, `grep -rlw` one by one in `src/`+`tests/` (excluding `src/locales/*`); zero hits are treated as suspected dead keys first, then the source is re-read by hand to rule out false positives from “dynamic subscript access”.
- **Confirmed dead keys (1)**: `O.services.apiKeyStored` (`zh-CN.ts:139` = `'已保存'`, `en.ts:133` = `'Saved'`) — **apart from its definition there is no second occurrence in `src/` or `tests/`**. The placeholder of the API Key input's saved state at `entrypoints/options/sections/ServiceDrawer.tsx:159` is actually the hard-coded string `'••••••••'`; the “shows ••••••••” the UI.md S-O-17 copy entry describes never matched this key's meaning (the word “saved”) in the first place, which looks like an old key left behind by a copy change.
- **3 false positives found by the scan (ruled out by hand)**: `S.mode.stackTitle`/`sideTitle`/`onlyTitle` had zero hits at first; re-reading the `modes()` function of `PopupView.tsx` shows the key name is assembled dynamically through the template string `` S.mode[`${value}Title` as const] `` (`PopupView.tsx:25`), which a static grep naturally cannot see — **not dead keys**.
- **`public/_locales/` (the two Chrome itself recognises, a second i18n system fully independent of the 234 above)**: `en/messages.json`, `zh_CN/messages.json` (note the directory name uses an **underscore**, `zh_CN`, a hard requirement of Chrome i18n, while the application's own pack uses a **hyphen**, `zh-CN` — two systems' own conventions, not a spelling mistake); exactly 2 keys each: `description` (the extension-management page / store blurb), `toggle` (the shortcut's description), matching the `__MSG_description__`/`__MSG_toggle__` placeholders at `wxt.config.ts:38,44` and `default_locale: 'en'`. These two keys are read by the browser alone, the language choice lies entirely on Chrome's side, and `pickLocale` of `src/locales/**` cannot reach them (the table in UI.md §6 says so explicitly too).
