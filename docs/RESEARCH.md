## 1. Fixtures

Ten papers are saved in `tests/fixtures/arxiv/<id>.html`; see that directory's `README.md` for the list and selection rationale. Coverage includes dense formulas (3 papers), algorithms/code blocks (4), large/numeric tables (4), footnotes/theorems (4), four papers from 2023, one each from 2024 and 2025, four from 2026, and two with `.ltx_ERROR` (including one failed-conversion page).

**Key findings**

1. **No pages generated by early LaTeXML versions remain online.** All 56 candidates (2023-12 through 2026-09) have generator comments identifying `LaTeXML oxide (version 0.7.6)`, including December 2023 papers. Versioned URLs such as `/html/2312.17127v1` also return oxide 0.7.6. arXiv has regenerated historical papers with the new converter, making older output unavailable. Therefore, online pages cannot currently satisfy the goal of covering LaTeXML version differences by year. Rules need to target only oxide 0.7.6, but version detection and branching should remain for future upgrades.
2. Not every paper has HTML: 4 of 60 candidates returned 404 because LaTeX source was absent or a failed conversion was not published. The extension only needs to handle existing HTML pages, with no additional detection.
3. Published failed-conversion pages exist (`2608.30667`): `<title>` is "Untitled Document", the body contains only one `.ltx_p`, and `.ltx_ERROR` identifies undefined macros. The extension must exit quietly or translate the available content without throwing an error.
4. Download notes: HTTP requests to `export.arxiv.org` redirect to HTTPS with 301, so curl needs `-L`; API ranges `[a TO b]` require `-g` to disable globbing; individual requests occasionally hang, so set `--max-time`; observe a three-second interval.
5. **Papers with old-style IDs also have HTML** (verified with curl on 2026-09-05 after Codex #9): `/html/hep-th/9901001` returns a complete LaTeXML page (`article.ltx_document`, title "String Junctions and Their Duals…"), and `/html/math/0601001` also returns 200. Therefore, `paperIdFromUrl` must accept `archive[.subject]/YYMMNNN[vN]`.

## 2. Rule Coverage Audit

### 2.4 Rule Redundancy and Priority

Combinations where the same unit element matches multiple rules: `p+theorem` 30,607, `p+item+theorem` 9,626, `p+item` 1,830, and `p+abstract` 150. The three §5.1 rules `.ltx_abstract .ltx_p`, `.ltx_item .ltx_p`, and `.ltx_theorem .ltx_p, .ltx_proof .ltx_p` are **entirely covered by `.ltx_p`**. Keeping them as independent rules violates the exactly-one-rule requirement. Remove them or turn them into context annotations informing the prompt that a block is a theorem or abstract, without participating in block classification.

### 2.5 Protected Nodes from §6.1 Must Enter the Rule Table

The audit used only the §5.2 skip rules, exposing that the void nodes listed in §6.1 are currently treated as paragraph text:

| Element | Elements with direct text | Notes |
|---|---|---|
| `a.ltx_ref` (including `span.ltx_ref_tag.ltx_text`) | 1045 + 1639 | Cross-references such as "Section 2", "Theorem 1", and their numbers |
| `cite.ltx_cite.ltx_citemacro_*` | 713 | Citation markers |
| `sup.ltx_note_mark` | 112 | Footnote markers appear once in outer `.ltx_note` and again inside `.ltx_note_content` |

They must be registered as void placeholders in `latexml.ts` (`PROTECT_RULES`), alongside `.ltx_tag`, `math`, `code`, and `.ltx_font_typewriter`. Another structural finding: **footnotes are nested blocks**. The entire `.ltx_note` (marker plus `.ltx_note_outer > .ltx_note_content`) sits inside `.ltx_p`, while `.ltx_note_content` is itself a translation unit. The outer paragraph must treat the whole `.ltx_note` as a void placeholder, with the footnote body extracted separately. The second `.ltx_note_mark` and `.ltx_note_type` ("footnotemark:", in only one paper) inside `.ltx_note_content` are void.

### 2.6 Table Cells and the §5.3 Numeric-Cell Regex

`scripts/phase0/td-numeric-calib.ts` measured 5,487 `.ltx_td` cells using visible text after excluding MathML subtrees: 271 blank, 294 formula-only, 3,236 matching the initial regex (59%), and 1,686 prose cells. The initial regex has two problems:

- **False positives**: `e` / `E` in the character class, intended for exponents, allows entire words beginning with E to match: `ERROR` 90 times, `Esp`, and `ESBMC`. Fix: require at least one digit with the lookahead `(?=.*\d)`.
- **False negatives**: `✓` 167 times, `N/A` 17 times, single letters `G` / `N` / `Y` / `S`, parenthesized units `(kpc)`, and `Au+Au`. Fix: add a symbol-only branch (`✓ ✗ ✔ ✘ – — −`) and `N/A`.

There are also 427 uppercase enum values `TRUE` / `FALSE` / `UNKNOWN` in one paper. These are values rather than prose, but a regex cannot distinguish them from abbreviations; leave them to the provider, since LLMs preserve them. Proposed regexes: `^(?=.*\d)[\s\d.,+\-±×^%()/*eE−–—:;~<>=≤≥∼]+(\s*[a-zA-Zμ°%]{1,4})?$`, or `^[✓✗✔✘–—−\-·×*]+$`, or `^N/A$`. Values with units such as `7.7 GeV` match correctly.

### 2.7 Code and Algorithm Boxes

- Listing containers use `.ltx_listing`, sometimes combined with `.ltx_lstlisting` or `.ltx_lst_language_*`; lines use `.ltx_listingline`, and line numbers use `.ltx_tag.ltx_tag_listingline`. Skip `.ltx_listing_data`, which contains hidden original code data.
- Algorithm boxes `figure.ltx_float.ltx_algorithm` (two papers) / `.ltx_float_algorithm` (one paper) contain `.ltx_listingline`, already covered by the code rule; their `.ltx_caption` remains translatable.
- `.ltx_verbatim` appears in two papers. Standalone `pre` / `code` tags do not appear in body content; all monospace text uses `.ltx_text.ltx_font_typewriter` (2,488 elements).

### 2.8 (c) Class Distribution

The translation roots contain 255 `ltx_*` classes, only two of which appear in all ten papers: basic classes such as `ltx_Math` and `ltx_p`. The long tail mainly consists of template classes (ACM `ltx_affiliation_*`, `ltx_role_*`), bibliography subdivisions (over 20 `ltx_bib_*` classes, only in 2609.00246), theorem types (`ltx_theorem_*`), and listing languages (`ltx_lst_language_*`). These all lie inside existing units and need no separate rules. Because every fixture uses oxide 0.7.6, this distribution reflects content rather than version differences.

### 2.9 SVG Share (§15.1)

The translation roots contain 164 `svg` elements, all `svg.ltx_picture` (TikZ): 114 in 2608.29808 and 43 in 2312.17141, mostly marked `ltx_markedasmath` because they depict formulas. **None contains `<text>`.** Text occurs only as `foreignObject > .ltx_foreignobject_content`, with just one text node across all fixtures. There are 13 bitmap `img.ltx_graphics` elements across five papers. Conclusion: SVG figures have effectively no translatable DOM text; v1 should skip entire `svg` elements, and the §15 OCR path is relevant only to `img`.

### 2.10 Other Findings

- `.ltx_p` is not always a `<p>`: 57 `span.ltx_p` elements occur in two papers, inside tables and inline-blocks. The §7.1 same-tag-as-original rule already covers this; the §7.2 grid technique can apply only to `.ltx_para > p.ltx_p`, with other cases falling back to stack.
- Text outside the translation root consists only of the table of contents in `.ltx_page_navbar` (`ltx_ref_title`, `ltx_tag_ref`, math/italic in TOC headings) and arXiv headers and footers, confirming that nothing outside the root should be extracted.
- Failed-conversion page `2608.30667`: four text nodes, two units, and no script errors. The extension should handle such pages quietly.

### 2.11 Rerun with RULES_VERSION 0.2.0 (Phase 1 `feat/rules`)

The audit now calls the rules module's `classify()` directly (priority skip > table > unit > protect; `.ltx_note` is protect-but-descend). The report has been regenerated at `docs/phase0/rules-audit.md`:

- **0 uncovered / 112,268**: acknowledgements, keywords, and subtitles became units; publication metadata, dates, and SVG became skips; `.ltx_note_mark` became protected.
- No dead rules; unit rules are mutually exclusive (`multi` is empty), satisfying exactly-one-rule coverage.
- Reclassification: `.ltx_ref` (3,253 text nodes), `.ltx_cite` (1,872), and `.ltx_note_mark` (114) moved from paragraph text to protected nodes; 4,632 table-cell text nodes belong to `table`; 166 footnote-body nodes belong to nested `footnote` units, with zero attributed to the `.ltx_note` container itself.
- Unit shares consequently fell, for example from 49.4% to 26.6% in 2401.00596. These are the correct numbers after excluding references and footnote markers from translatable text.

### 2.12 Checking Rule Coverage Against CSS Classes (2026-09-04)

The initial hypothesis was that ar5iv CSS covers every block and could therefore complete the rules. **Measurements disproved it.**

Combining all 15 stylesheets under LaTeXML `lib/LaTeXML/resources/CSS`, including template-specific `ltx-book.css`, `ltx-amsart.css`, and `ltx-apj.css`, with the ar5iv repository and the two stylesheets actually served by arXiv yielded **322 `ltx_*` classes**. Twenty additional papers from eight subject areas were then downloaded for comparison:

- **88 classes occur in pages but in none of the CSS**, including major classes: `ltx_Math` 20/20 papers, `ltx_ref_tag` 20/20, `ltx_tag_bibitem` 20/20, `ltx_math_unparsed` 18/20, `ltx_citemacro_cite` 17/20, plus the `ltx_theorem_*` and `ltx_bib_*` families.
- **Class names form an open set**: `ltx_theorem_maintheoremA`, `ltx_theorem_manualconjectureinner`, `ltx_bib_<field>`, `ltx_citemacro_<macro-name>`, and `ltx_colspan_8` are generated from authors' LaTeX macros. No stylesheet can enumerate them all.
- Conversely, **145 classes appear only in CSS**: book, CV, index, epigraph, and other template-specific structures absent from all 30 real papers.

Coverage check using `classify()` for each text node: **20 new papers plus 10 fixtures contain 36,348 text-bearing nodes, with one uncovered**. It is an MSC classification code in a mathematics paper (`.ltx_classification`), which should not translate anyway.

Conclusion: exhaustive class enumeration cannot complete the rules. Coverage comes from the structural property that containers need no rules and text falls inside a small number of units such as `.ltx_p`. The CSS list is useful for the third finding: those 145 unseen structures are now represented in `tests/fixtures/arxiv/synthetic-structures.html` following LaTeXML output conventions. Running it exposed eight real gaps (`.ltx_date`, `.ltx_role_dedicatory`, bare description-term text, `.ltx_marginpar`, `.ltx_indexentry`, and CV fields), now added to the rules.

The originally reported missing translations, acknowledgement-like author notes, were unrelated to rule completeness. They came from the §5.2 policy of skipping the whole author area, changed to translate by default in the same revision.

## 3. Containers and Navigation

### 3.1 Page Structure (oxide 0.7.6 + arXiv Theme 2026-08)

```
body                                  ← display:grid at ≥1280px (see 3.2)
├─ header.arxiv-html-header           ← injected by arXiv: logo, nav.html-header-nav
├─ nav.ltx_page_navbar                ← LaTeXML navigation containing nav.ltx_TOC
├─ div.ltx_page_main
│  └─ div.ltx_page_content
│     └─ article.ltx_document         ← paper body, max-width: var(--main-width)
├─ footer.arxiv-html-footer           ← injected by arXiv
├─ footer.ds-site-footer              ← injected by arXiv (site footer)
└─ other arXiv elements: #infobox, #watermark-tr, .keyboard-glossary, #fixed-buttons-container,
   issue-report modal (.modal-header / .modal-body / .modal-footer, form #modal-form), .ds-announcement
```

Main-container rule: use `article.ltx_document` as the translation root. Exclude `.ltx_page_navbar` and all injected elements without the `ltx_` prefix from extraction.

### 3.2 Width Control (Determines the Side-Mode Approach)

- The sole width source is CSS variable `--main-width`, defined as `52rem` in the ar5iv stylesheet's `:root`.
- `.ltx_document { max-width: var(--main-width) }`; `.ltx_page_main { width: 100% }` imposes no width cap.
- At `@media (min-width: 1280px)`, the arXiv theme sets `body` to `display: grid; grid-template-columns: 1fr var(--nav-width) var(--main-width) var(--nav-width) 1fr`, with `--nav-width: minmax(14rem, 25rem)`. `div.ltx_page_main` occupies the `article` area, and `nav.ltx_page_navbar` occupies `nav`.
- Therefore, **side mode needs only to override `--main-width` on `html[data-axt-mode="side"]`**, for example with `min(1600px, 96vw)`. The article column and `.ltx_document` widen together without changing `.ltx_page_main`.
- Side effects: image max-width rules (`.ltx_graphics`, `.ltx_img_*`), code blocks `.ltx_listing`, cells `.ltx_td`, and absolute footnote positioning at ≥96rem (`--main-width-margin`) also reference the variable, so they grow with it. Wider images are generally acceptable; if not, pin their `max-width` rules back to `52rem` in side mode.
- Breakpoints: the arXiv theme uses 1280px for collapsed navigation/header, matching JS `narrowViewport`. ar5iv also uses 46/52/96/109rem, with 96rem selecting popup versus marginal footnotes. The DESIGN.md §7.2 automatic fallback threshold of 1100px matches neither system; change it to 1280px to align with arXiv.

### 3.3 arXiv Page JavaScript (`/static/browse/0.3.4/js/arxiv-html-papers-*.js`, 268 Lines)

- It touches only three DOM areas: `html` attributes `data-theme`, `data-toc-display`, and `data-reading-mode`, persisted in localStorage as `ar5iv_theme`, `arxiv_html_paper_toc_display`, and `arxiv_html_paper_reading_mode`; visibility of `.ltx_page_navbar > nav.ltx_TOC`; and a `mouseup` listener on `.ltx_page_content` that saves selection `innerHTML` for the issue-report form.
- **No** MutationObserver, **no** MathJax (zero occurrences; formulas use native MathML), and **no** footnote JavaScript.
- Footnote popups use CSS only: below 96rem, `.ltx_note:focus-within > .ltx_note_outer` opens the popup; at ≥96rem, `.ltx_note.ltx_role_footnotetext .ltx_note_outer` becomes an absolutely positioned marginal note. Cloned translation footnote markers can trigger the same popup as long as the structure matches; no extra handling is needed.
- Conflict surface: almost none. If a user selects translated text and opens the issue-report form, the saved selection HTML includes `.axt-t` nodes, which is harmless.
- Header script `arxiv-header.js` manages only site banners and announcements, not paper content.
- Inline `<script>` elements only restore the above preference attributes early; inline `<style>` elements total just 535 bytes.

### 3.4 arXiv Reading Mode Versus Extension Modes

arXiv `data-reading-mode=enabled` hides `header.arxiv-html-header` and `.ltx_page_navbar`. If side mode needs to hide navigation, use `html[data-axt-mode="side"] .ltx_page_navbar { display:none }` directly. Do not set arXiv's own attribute, which its scripts would persist to localStorage.

### 3.5 Site Rules for Lists and Multipanel Figures (2026-09-05, `ar5iv.0.9.1.min.css`)

Stylesheet entry `/static/browse/0.3.4/css/arxiv-html-papers-20260823.css` contains only two `@import` statements: `ar5iv.0.9.1.min.css` into `layer(ar5iv)` and `arxiv-html-papers-theme-20260807.css` into `layer(arxiv-theme)`; download with `curl -L`. Rules directly relevant to side-mode lists:

- `li.ltx_item > .ltx_tag { display: inline; margin-inline-start: -2.5rem; padding-inline-end: .5rem; text-align: end }`: itemize markers hang by 2.5rem, the source of the 2.5rem marker slot in modes.css.
- `.ltx_enumerate { display: grid; grid-template-columns: max-content minmax(0, 1fr); column-gap: .5em; padding-inline-start: 0 }` and `.ltx_enumerate > .ltx_item { display: grid; grid-template-columns: subgrid; grid-column: 1 / -1 }`: enumeration marker columns follow **content width**, so long labels such as "(Assumption 1)" fit the original layout. Our fixed 2.5rem absolute slot can overflow (Codex #25), but the site exposes **no** variable such as `--ltx-enum-leftmargin`, so the proposed variable-based measurement is not viable.
- Nested-list indentation comes only from `.ltx_item > .ltx_para > :is(.ltx_enumerate, .ltx_itemize, .ltx_description) { margin-inline-start: var(--space-xs) }` plus the inner list's own marker column. Absolute positioning of side-mode markers loses this indentation (Codex #25, the (k.i) list in 2609.00245); address it with the real-browser layout tests.

Rules directly relevant to the side-mode **width contract** (added 2026-09-05, DESIGN §7.2):

- Theme `body { grid-template-columns: 1fr var(--nav-width) var(--main-width) var(--nav-width) 1fr; grid-template-areas: "... . nav article . ." }`, with `--nav-width: minmax(14rem, 25rem)`; column four has no named area. Native measurements: `0 224 832 224 0` at 1280px; navigation caps at 400px for widths ≥1800px.
- `.ltx_page_content { margin: 1rem }` overrides ar5iv `var(--space-xl) var(--space-sm)`. The two columns therefore have the article-track width minus 2rem available.
- ar5iv right gutter: `.ltx_note_outer` is shown only at `@media (width >= 96rem)` with `float: inline-end; padding-inline-end: 3rem; position: relative`. Widths are fixed by breakpoint: `width: 20rem; margin-inline-end: -24rem` for `96rem < width <= 109rem`, and `27rem / -31rem` for `> 109rem`. At `< 96rem` it uses `display: none` and opens on `:focus-within`. `.ltx_note.ltx_role_footnotetext .ltx_note_outer { position: absolute; inset-inline-start: var(--main-width-margin) }`; `--main-width-margin: 54rem` is used only here across the site.
- `.ltx_pubnotes.ltx_pubnotes_meta .ltx_pubnotes_content { float: inline-end; width: min(27rem, calc((100vw - var(--main-width)) / 2 - 2rem)); margin-inline-end: calc(1rem - (100vw - var(--main-width)) / 2) }`. `.ltx_note.ltx_note_frontmatter.ltx_role_thanks` uses the same width with `position: absolute; inset-inline-end: calc(1rem - (100vw - var(--main-width)) / 2)`, relative to the article's right edge. Author-area `.ltx_authors ... :last-child.ltx_role_affiliation / .ltx_role_address { position: absolute; width: min(var(--main-width), 100dvw); inset-inline-start: max(0px, calc((100dvw - var(--main-width)) / 2)) }`. All four groups assume a centered article with equal gutters.
- Theme `@media (max-width: 1279px)` converts navigation into a `position: fixed` drawer, matching the `responsive.ts` stack fallback breakpoint.
- `ltx_flex_size_N` specifies LaTeXML flex-cell fractions: `size_1` is full width, `size_2` half width, and `size_3` one-third. Fixtures contain 21 size_1 cells and 13 size_2/3 cells. Single-column flex figures, whose cells are all size_1, commonly hold a table plus footnote, such as Table 1 in 2609.03768v1.

## 6.7 Request Location: Content Fetch Faces Both CORS and Local Network Access Restrictions (2026-09-05; Mixed-Content Attribution Corrected 2026-09-06 Below)

**Method**: run two otherwise identical local OpenAI-compatible endpoints differing only in CORS headers. `/v1/chat/completions` supplies `Access-Control-Allow-Origin: *` and answers preflights; `/nocors/...` supplies no CORS headers. Load a probe extension in Playwright with endpoint `host_permissions`, then send the same POST with `Authorization` from the **background service worker**, **content-script isolated world**, and **page main world**. The server records Origin, preflights, and status. The probe lives in the session's temporary directory, outside the repository.

| Execution context | Endpoint with CORS headers | Endpoint without CORS headers | Server-observed Origin / preflight |
|---|---|---|---|
| Background service worker | 200 | **200** | `chrome-extension://<id>`, **no preflight** |
| Content script, isolated world | 200 after `OPTIONS` preflight | **`TypeError: Failed to fetch`** | Page origin `http://localhost:8898`; preflight sent, then failure because the response lacks CORS headers |
| Page main world | Same as content script | Same as content script | Same as above |

Changing the page to real `https://arxiv.org/html/...` while keeping the endpoint at `http://127.0.0.1` made page fetch fail immediately with `Failed to fetch`. **The request never left the browser**: server logs were empty. Background still returned 200.

**This was initially attributed to mixed-content blocking, incorrectly** (Codex #57; follow-up measurements corrected it on 2026-09-06). Loopback is a *potentially trustworthy origin* under the specification, so an HTTPS page calling `http://127.0.0.1` **is not mixed content**. The follow-up control ran `http:8901` and `https:8902` on the same loopback host, with a self-signed certificate and `--ignore-certificate-errors`. Both endpoints returned `Access-Control-Allow-Origin: *`:

| Initiating page | → `http://127.0.0.1:8901` | → `https://127.0.0.1:8902` | Server received |
|---|---|---|---|
| `http://127.0.0.1:8901`, also local | **200** | **200** | Both preflight and POST |
| `https://arxiv.org/html/...` | `Failed to fetch` | **`Failed to fetch`** | **Nothing** |

The first row rules out certificate, endpoint, and CORS explanations. The second blocks HTTPS → HTTPS too, which cannot be mixed content. **Chrome's Local Network Access gate from public sites to local addresses is the actual restriction**, independent of endpoint scheme.

Practical consequence: **an HTTPS certificate on the local endpoint does not bypass this restriction**. Direct page-side Ollama access is blocked; background works because an extension origin with `host_permissions` is not subject to this gate. In the same experiment, background returned 200 from both endpoints.

**Conclusions**:
1. Under MV3, `host_permissions` **does not remove content-script CORS restrictions**. Requests use the page origin and preflight exactly like the page main world. This has been Chrome behavior since version 85; see developer.chrome.com/docs/extensions/develop/concepts/network-requests.
2. Background requests use the extension origin without preflight and work with endpoints lacking CORS headers.
3. Public pages cannot reach local endpoints because of **Local Network Access restrictions**, regardless of scheme, as the controls above demonstrate. Local Ollama at `http://localhost:11434` is **unreachable from content** but reachable from background. In the then-current architecture, Ollama listed in CLAUDE.md could pass only the settings connection test, which ran in background; actual translation in content necessarily failed. This mismatch is the issue identified in #42.
4. Direct content access to public APIs such as OpenRouter / DeepSeek depends on their continued support for browser CORS headers, an external condition beyond our control. Background does not depend on it.

**An error in §6.5**: that section claimed Read Frog puts provider fetch in content scripts and excludes the service worker entirely. Checking the reference snapshot showed `utils/host/translate/translate-text.ts:360` sends `sendMessage("enqueueTranslateRequest", …)` to background, and `entrypoints/background/translation-queues.ts:490` queues and actually invokes the model in the worker. Read Frog **does execute requests in background**, along with waiting and queueing. The 6.7–77 s in §6.5 **was an observed delay**, but its attribution to worker cold start was never verified because worker state was not recorded; see the retest limitations below. It also cannot be reproduced in current code. The reference-project explanation was unsupported too, invalidating its use in DESIGN §8.0 as a reason to move requests into content.

**Cold-start latency retest (2026-09-05, Playwright + current main build)**: timed `axt:ping`, cold/warm `axt:provider-status`, and `chrome.storage.local.get` from the popup. All four rounds, immediately after startup and after three separate 36-second idle periods, fell within **0–5 ms**:

| Round | Live workers before measurement | ping | Cold provider-status | Warm | storage |
|---|---|---|---|---|---|
| After startup | 1 | 5 ms | 1 ms | 1 ms | 0 ms |
| Three 36-second idle periods | 1 / 1 / 1 | 1 ms | 1 ms | 0–1 ms | 0 ms |

Two conclusions: (1) **steady-state cost is roughly 1 ms** for `getConfig()` + `getProvider()` + `isAvailable()`, so the 6.7–77 s in §6.5 was not intrinsic code overhead; (2) **Playwright never reclaims the worker**. All three idle periods still left one live worker because debugger-attached workers are exempt from MV3 idle reclamation. The CDP `ServiceWorker` domain was also unavailable in the browser-level session, so §6.5's cold-worker condition **could not be reproduced here**, preventing the three-part timing breakdown in automation. **Retest in real Chrome (2026-09-06, Chrome 152, the user's browser, driven by Claude in Chrome, build `c24ebbd`)**: close all extension pages, idle for 40 seconds, exceeding MV3's 30-second threshold, then reload the paper and read content logs. In this architecture the only startup message content sends to background is `axt:cache-get`, so the time to complete all 13 blocks from cache is an **upper bound on a message round trip plus IndexedDB reads on a cold worker**:

| Round | `start: ready` | `session idle`, all 13 blocks cached | Cache-read timeout warning / channel closed |
|---|---|---|---|
| Initial load, warm | 33 ms | 1633 ms (13 requested, 1 cached, using google-web) | None |
| 40-second idle #1 | 4 ms | 77 ms | None |
| 40-second idle #2 | 22 ms | 81 ms | None |
| 40-second idle #3 | 21 ms | 77 ms | None |

**This table does not measure cold start and must not be used as cold-start evidence** [Unverified] (Codex #57 / #78, two rounds). It did not directly observe whether the worker had actually been reclaimed before each reload. Forty seconds **exceeds** the MV3 30-second threshold, but Chrome may delay reclamation and extension API activity resets idle timers. These 77–81 ms values could therefore all come from warm workers. Worker ages in §6.8 (45,013 ms / 90,007 ms, matching request duration) prove only that **reclamation was occurring on that machine**. That experiment used a different 12-line probe and measured survival during slow fetches, **not this extension's initialization, configuration reads, or chain construction**.

This table supports only **roughly 80 ms steady-state round trips with a warm worker**. The claim that a cold worker would be only slightly slower is speculation without measurements, and this section no longer makes it. Verification requires worker-creation instrumentation in the extension's own background and a complete first-message round trip after restart.

Across three **reloads after idle**, without directly observing whether workers were cold or warm, background round trips were within 80 ms and the 1.5-second cache-read budget never fired. **The 6.7–77 s in §6.5 cannot be reproduced in current code.** That measurement used a version whose cache writes still scanned the entire database (fixed in §9); it also routed `provider-status` through background, whereas current startup bypasses it. Thus the **latency** rationale in §8.0 for moving requests to content is unsupported. Again, failure to reproduce is not proof of fast cold starts. The **CORS / Local Network Access** costs are directly established here. ## 6.8 MV3 workers survive long in-flight requests without keepalive (2026-09-06, Chrome 153, the user's browser)

**Why this needed a separate test**: §6.7 measured only **startup** round trips (77–81 ms). The `A listener indicated an asynchronous response by returning true, but the message channel closed` error recorded in §6.5 is a different failure mode: the worker is reclaimed **after a request has been sent, while it is waiting**. Neither test proves the other, and the viability of moving translation back to background (issue #42) depends on the latter. Playwright's debugger pins workers so they are never reclaimed (as recorded in §6.7); this must be tested in real Chrome.

**Method**: a 12-line probe extension (in a session temporary directory, outside the repository), with `host_permissions` covering a local endpoint. A local HTTP server exposed `/slow?ms=N`, responding after N milliseconds. The content script used a one-shot `chrome.runtime.sendMessage` to ask background to fetch it, **without any keepalive**, after first leaving the worker idle. The debugger attached only to the page, never to the worker.

| Delay | Result | Elapsed | Worker age |
|---|---|---|---|
| 45 s | OK | 45 063 ms | 45 013 ms |
| 90 s | OK | 90 052 ms | 90 007 ms |

Both runs far exceeded MV3's 30-second idle-reclamation threshold, and responses returned to content normally. **Conclusion: an in-flight request itself keeps the worker alive; no Port or heartbeat is needed.**

**This conclusion covers only waiting while a fetch is in flight** [Unverified] (raised by Codex in #78). After a 429, `RequestQueue` lets that fetch finish normally and leaves the task waiting on `setTimeout` for backoff (`Retry-After` or exponential backoff). During that interval, **there is no active request**, and the end-to-end budget can reach 180 s, far beyond the 30-second threshold. This probe also did not distinguish whether the pending content-side `sendMessage` or the active fetch kept the worker alive. Covering that interval requires a probe that makes background wait N seconds after receiving the message before starting fetch. The current fallback is that an actual failure would time out that batch; the fallback chain and retries would still work, without stalling the whole page. The other two prepared variants (holding `chrome.runtime.connect` for the session, or pinging every 20 s) did not need to be enabled. The cause of §6.5's error was not reproduced; it may have been a long block caused by cache writes scanning the entire database at that time (fixed in §9).

**Incidental test: `Translator.create()` in background.** §6.4 established that workers expose `Translator` and that `availability()` matches the popup, but did not test `create()`. This time, the probe read `downloadable` in the worker (the language pack was not ready in that Chrome profile), **so `create()` could not be tested** and remains unknown. This does not block the move: `buildChain` already removes engines whose `isAvailable()` returns false, so `chrome-builtin` is automatically excluded when its language pack has not been downloaded. A download must be initiated by a popup click gesture anyway (§6.1). Retest when the language pack is ready.
