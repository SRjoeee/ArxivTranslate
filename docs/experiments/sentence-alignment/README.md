# 实验：句子级对照与纯文本占位符（2026-09-08）

这个分支只存**测量数据与探针脚本**，不含任何实现。做左右对照阅读（悬停某句 → 高亮原文对应句）时切回这里，数据都在，不用重跑。

脚本里的路径是硬编码的绝对路径（当时在 scratchpad 里跑的），复用前要改。

## 起因

用户问：沉浸式翻译用免费非 LLM 引擎，为什么每个节点都保护得很好？把它的扩展复制一份加载进 Playwright 做黑盒观察（只看请求形状与 DOM 结构，**不读、不抄它的打包代码**——闭源商业产品，与本项目 GPL-3.0 不兼容）。

## 一、沉浸式翻译的实际做法（`scripts/oracle.mjs`、`it-probe*.mjs`）

它的 content script 匹配 `<all_urls>`，所以可以起本地服务器喂构造好的测试页，精确地问它「遇到这种情况你怎么办」。

- 记号 `@N#`，**编号块内局部、每块从 0 重新开始**；记号两侧补空格
- 整段一起送，线上传纯文本；打到的正是 #98 那个微软免鉴权端点
- 内联元素（`<em>` / `<strong>` / `<a>` / `<cite>`）**一律拍平**，译文 DOM 里只剩 `font`——**链接因此点不动**
- 只有公式没有文字的块不发送
- 整页攒成一个请求
- 译文**插进原节点内部**（我们不能学，违反 §7.1）

**它的两个缺陷**（`data/oracle-sent.json`）：

1. 不转义正文里的字面量记号。构造一段同时含字面量 `@0#` 与真占位符的文字，渲染结果是「字面标记 w 和实公式 w」——公式被克隆进两个位置，原文字消失。
2. 记号被引擎复制时它照单全收。30 个记号那段实测 `trMath: 31`，译文里同一个符号出现两次。

## 二、线上格式：按引擎选，不是全局换一种（`scripts/baseline.mts`）

90 个真实块、400 个占位符：

| 线上格式 | 微软 | Google |
|---|---|---|
| 现在的 `<x id="N"/>` 标签 | **0%**（400 个全丢） | **100%** |
| `@abc#` 纯文本记号 | 98% 块 / 99.3% 记号 | 93% 块 / 96.8% 记号 |

结论：**保留两套**。Google 走标签（100%，零改动），微软等只收纯文本的引擎走记号。整体换成记号是净损失。

### 记号语法对比（`scripts/bakeoff.mts`）

- **字母 id 明显优于数字 id**：`@abc#` 在 Google 上 93% 块，`@N#` 只有 79%。数字太像引用编号，会被改写成「第 1 节」「表 1」
- **私用区字符（U+E000+）被微软整个吞掉，0% 存活**，淘汰
- 冲突率 0：12 篇 fixture、725572 字符里，所有候选记号的完整形式一次都没出现过（裸 `@` 5 次全是邮箱，裸 `#` 1 次是 F#）

### 成对记号不可用（`scripts/paired.mts`）

80 个含成对占位符的块、275 个 void、143 个 paired：

```
                块完好   void      paired
扁平  微软        99%    99.6%      —
扁平  Google      95%    98.5%      —
成对  微软        85%    99.6%     92.3%
成对  Google      63%    95.6%     70.6%   ← 42/143 直接丢
```

只能像沉浸式翻译那样拍平。代价：占位符里 23.4% 是成对的，49.2% 的块至少含一个。**但我们比它强的地方**：带功能的元素（链接）按 void 处理保住可点击，`runs.ts` 里 issue #44 那条规则直接继承。

### 开销（`scripts/cost.mts`）

```
markup 线上载荷  894 KB
marker 线上载荷  745 KB   −16.7%（记号比标签短）
送出段数         都是每块一段（runs 路径是每块 3.43 段）
splitRuns 额外耗时 10 ms（12 篇合计）
```

**性能是净收益**，不是代价。marker 路径应建在 `splitRuns()` 之上，不要另写序列化器。

## 三、句子级对齐

### CSS Custom Highlight API 可用（`scripts/highlight-api.mjs`）

```
supported: true, Chrome 153, domUnchanged: true
```

高亮任意 Range **完全不碰 DOM**，与 §7.1 天然兼容。原文侧不需要（也不允许）包 `<span>`。

### 两条产生对齐的路

**A. 句子边界记号**（`scripts/sent-align.mjs`）：微软 3/3 段对齐，Google 2/3（第三段边界记号全丢）。失败是软的——那段没有高亮，译文完好。

**B. 按句切分成独立段送**（`scripts/quality.mts`，40 段真实语料）：

```
微软    逐字相同 37/40，相似度中位 1.000
        sentLen [140,84,157,227,147] ← 它内部本来就按句切
Google  逐字相同 0/40，相似度中位 0.919，p10 0.811
```

> ## ⚠️ 2026-09-09 更正：本节原来的两条结论已撤回
>
> 原文写的是「**微软按句切分零质量代价**（本质是句子级模型）」以及「微软走 B，对齐 100% 精确且免费」。
> 同事在 issue #105 的审阅中指出这两条推不出来，逐条复核后确认**他是对的**：
>
> **1. `quality.mts` 的 `sim()` 是字符频次比较，完全不看顺序。** 按它的实现跑反例：
>
> ```
> 甲击败乙 vs 乙击败甲          → 1.000
> 模型优于基线 vs 基线优于模型   → 1.000
> ```
>
> 在翻译论文这个场景里，把比较关系译反正是最该被抓住的错误，而这个指标给它满分。
> 所以「相似度中位 1.000」**不支撑任何结论**。`逐字相同 37/40` 是字符串全等、顺序敏感，仍算证据，
> 但只能说「这批样本的两种输出高度接近」，到不了「零质量代价」，更到不了「本质是句子级模型」。
> 那 3 段不相同的，恰恰只用这个坏指标评估过。
>
> **2. `sent-align.mjs` 的 `OK` 判定只比较记号数量**，且只有 3 个手写段落。
> 预期 `@sa# @sb# @sc#`、返回 `@sa# @sa# @sc#` 也会判 OK。所以「微软 3/3、Google 2/3」
> 说的是**记号数量**，不是句子映射正确。记号完整性、语义对齐正确率、对齐覆盖率是三件事。
>
> **3. `@sa#` 与生产占位符语法直接冲突。** 拿仓库里真实的分词器跑：
> `tokenize('@sa# 第二句 @sb# 第三句', 'markers')` → `@sa#` 被解析成 **id 495 的受保护占位符**。
> 真接进生产，`validate` 会报 `unknown id 495`、整块译文被拒。对齐信息需要独立的词法类别或元数据通道。
>
> **还漏掉了一条更好的路**：微软响应里的 `sentLen`（上面那行数字就是它）是**原生句边界**——
> 如果可靠，根本不需要为了高亮去切句或注入记号，保持整段翻译即可。这条当时看见了却没往这个方向想。
>
> 后续验证顺序见 issue #105 的评论。**在实验判定被修正之前，本文档的结论不作为设计依据。**

**Google 确实用跨句上下文**，切了会掉术语一致性，实测有一处把 conditioning 误译成「条件反射」——这一条是逐字对照人工看出来的，不依赖上面那个坏指标，仍然成立。

### 切句器本身是风险

微软那 3 处失败全是参考文献里的 `Phys. Rev.` 被当成句号断开，翻成「物理学。牧师。」。§5.4 的参考文献块应直接不做句子切分；正文里的缩写要认真处理。`scripts/build-eval.mts` 里的 `ABBR` 正则是当时用的版本。

## 四、免费引擎盲评（`scripts/build-eval.mts`、`data/eval-sheet.md`、`data/eval-key.json`）

38 段真实块，跨 12 篇 9 个学科，A/B 随机打乱、占位符统一显示成 `⟦n⟧` 以免语法泄底，打完分再揭晓。**评委是我（单一 LLM 评委），不是人类评审团，结论当参考。**

**Google 22 胜，微软 11 胜，5 平。**

### 一个已确认的方法学缺陷

我没有归一化空白就送出去了。fixture 的 HTML 原文带换行符，微软会原样保留并近似逐行翻译，Google 内部会归一化。`scripts/ws.mjs` 验证：归一化后微软那几段完全正常。**至少 4 段是因此失分的**，最坏情况修正后是 18 : 15，排序不变但差距小得多。

→ **归一化空白是接任何 marker 路径引擎前的必改项**。现在 `src/core/pipeline/batches.ts:25` 只对标题归一化，正文原样送。

### 两者的错法不同

- **微软弱在专业术语**：Galactocentric → 半乳系、Myr → 米尔、1 Gyr → 金刚期、rapidity → 快速、data race → 数据竞赛/数据种族（同段不一致）、barrier → 障碍物
- **Google 弱在数学语域**：total order → 总订单、"one has" → 一个人有、"Let X be" → 让 X 是（应为「设」）、Figure → 数字
- **学科倾向**：两篇纯数学论文（math.AP / math.OC）微软 4:2 领先，物理与 CS Google 压倒性赢。样本小，方向明确

### 主力引擎建议：维持 Google

| | Google | 微软 |
|---|---|---|
| 盲评质量 | 22 胜（最坏 18） | 11 胜（最好 15） |
| 占位符完整率 | **100%**（现有标签路径） | 99.3%（需记号路径） |
| 内联样式 | **全保留** | 49.2% 的块要拍平 |
| 实现成本 | **零**，已在跑 | 记号路径全套 |

微软的价值是**第二免费引擎的韧性**（硬规则 4），以及**承担句子对齐**——做悬停对照时它反而是更合适的那个。

## 五、现成实现调研：没有可搬的

- 三个参考仓库都没做真正的逐句对齐。FluentRead 的 `bilingualSentenceHighlight.ts` 只有 15 行，是个开关属性，真正的高亮是 `page.css` 里 `.fluent-read-bilingual:hover` 的**整块**高亮

**我们的处境更好**：那些工具没有翻译过程的控制权，只能事后猜；我们控制请求，可以让对齐在翻译时免费产生。

## 六、2026-09-09 续测：Google 的句边界，以及一条把前面数据都污染了的 bug

### 空白归一化不是「盲评方法学瑕疵」，是生产 bug（→ #119）

第四节把它记成盲评的失分原因，低估了。实测 12 篇 fixture：**3847 个正文块里 2373 个（62%）带硬换行**，
`batches.ts` 只归一化章节标题，正文原样送出。后果两条：

1. **微软把每个换行当句号**。同一段唯一差别是 `\s+ → ' '`：`state explosion` 从「状态爆炸」变成
   「**州级爆炸性质**」；`srcSentLen` 从正确的 2 句变成 5 句。
2. **60 段实测，未归一化时 266 个切点里 128 个是假边界（48%）**；归一化后 140 个切点只有 5 个假（3.6%）。

**因此第三节 B 与 issue #105 上报的 `sentLen` 数据全部是在被污染的输入上测的**，句数一项作废；
分割完整性那条两种输入下都成立，不受影响。脚本：`scripts/sentlen-whitespace.mts`。

### Google：注入独立标签，对齐精确

`translateHtml` 没有 `sentLen`，只能注入。用归一化后的 `srcSentLen` 切源句，每句前插一个空标签：

| 50 个多句块 / 190 句 | `<y id="N"/>` 自造 | `<s id="N"/>` 真 HTML 标签 |
|---|---|---|
| 标签存活（恰好一次） | **50/50** | 44/57 |
| 顺序正确 | **50/50** | 44/57 |
| 占位符落到正确句段 | **264/264 个 · 44/44 块** | 199/199 · 36/36 |

**标签名必须自造**——`<s>` 是删除线，Google 特殊对待它，13/57 丢掉。

第三行替代了第三节那个被撤回的坏指标：**顺序敏感、客观**——源句 i 里的 `<x id="k"/>` 必须落在译文第 i 段。

### 插标签的代价：改写，未见劣化

去标签去空白后与不插标签的译文比**编辑距离**（顺序敏感；绝不再用 `quality.mts` 的字符频次 `sim()`）：

```
完全相同     5/50
相对编辑距离 中位 5.2% · p90 28.0% · 最大 44.2%
```

差异最大的三例逐句人工读：**是改写不是劣化，插标签那版持平或更好**（不插标签的把 `7B model` 译成
「70 亿个词元」、把句号点在占位符前面）。**只有 3 例、评委是我**，所以只能说「未观察到劣化」。

### 两条路的形状

| | 边界来源 | 对齐精度 | 代价 |
|---|---|---|---|
| 微软 | 原生 `sentLen`，白拿 | 待测 | 无 |
| Google | 注入 `<y id="N"/>` | 264/264 零错位 | 译文被改写（未见劣化） |

**两条路都不碰 `@` 记号语法**，第三节撤回说明里那个协议冲突在两条路上都不会发生。

## 七、#122 合入后，用生产路径重测（2026-09-09）

前面所有数据的空白折叠都是实验脚本里手动 `\s+` 做的，与线上不一致（线上是 `[\t\n\f\r ]+`，保留 NBSP）。
#122 把折叠放进 `serialize` 之后，直接走生产路径 + 微软实际用的 `markers` 格式重测 60 段：

```
含硬换行            0 段        ← 折叠生效
含 NBSP             11 段       ← 保留生效
切点落在句末标点后  128/133  (96.2%)
切分完整            60/60       ← 手动折叠时是 58/60
记号完好的块        55/60  (92%)
记号逐个存活        345/351 (98.3%)
```

**两条结论**：

1. **保留 NBSP 不影响切分质量**——96.2% 与手动折叠（把 NBSP 也折掉）时的 96.4% 在同一水平，
   所以 #122 那个「只折 HTML 五空白」的收窄没有代价。
2. **切分完整率从 58/60 变成 60/60**。之前那两段的偏差是「译文以 `\n` 结尾、末段不算尾部空白」，
   折叠之后不再出现，`sentLen` 可以直接当索引用，消费方不需要再夹末段。

记号存活 92% 块 / 98.3% 记号，与 §2 的基线（98% 块 / 99.3% 记号）同一量级；这批样本更长、
每块记号更多（351 个 / 60 块 vs 基线的更小块），块级通过率因此低一些。

脚本：`scripts/sentlen-production.mts`。

## 八、插句标签的质量代价：盲评（2026-09-09）

§六 只人工读了差异最大的 3 例就说「未观察到劣化」，样本太小。补做盲评：21 组多句块，
每组随机决定插标签的那版排「甲」还是「乙」，占位符统一显示成 ⟦n⟧，判完写进
`data/tag-blind-verdicts.json` **再**对 `data/tag-blind-key.json`。

```
插标签胜 10    不插胜 9    平 2
```

**没有可测的差异。** 判据是「作为这段英文的中译哪一版更好」，看的是术语准确、语序自然、有无漏译。
双方各自都出现过严重错译——不插的把 `subjects` 译成「课程」、`Table` 译成「桌子」、
`a thread` 译成「一根线」；插标签的把 `string diagram` 译对成「弦图」而不插的译成「字符串图」，
但也把 HVS 译成「高亮度超新星」。**错法分布在两侧，不成系统。**

**一个被证伪的中途假设**：判到一半时注意到有一版经常在句末丢标点（括号不闭合、句号缺失），
猜那是插标签的那版——因为标签被剥掉后各段直接拼接。对完答案，这个模式**在两侧都有**，
不是插标签造成的。没有先下这个结论是对的。

**这个样本量能排除什么、不能排除什么**：21 组里 19 组分出胜负，10:9 与掷硬币无法区分，
所以它排除的是**大效应**；要分辨 65:35 这种量级的差异需要约 100 组。结论只能是
「没有观察到大的质量代价」，不是「两者等价」。

评委仍是单个 LLM（我），且实验也是我设计的。

脚本：`scripts/tag-blind-eval.mts`（出题）、`scripts/tag-blind-score.mts`（对答案）。

## 九、内容脚本的隔离世界能不能画出高亮（2026-09-09）

§三 里那句「CSS Custom Highlight API 可用，`domUnchanged: true`」是用 `page.evaluate()` 验的，
而那是**页面主世界**。真正要问的是：**我们的内容脚本跑在隔离世界，它注册的高亮页面会不会绘制。**
两个世界的 `window` 是分开的，这件事不是显然的。

写了一个一次性扩展（`scripts/highlight-isolated-world/`，内容脚本**不**声明 `world: "MAIN"`），
在真实 arXiv 页面上「注册 → 清除 → 再注册」，每步截同一个段落的图比对哈希
（`::highlight()` 无法用 `getComputedStyle` 查，只能看像素）：

```
隔离世界的 API   hasHighlights ✓  hasHighlight ✓  hasCaretPos ✓
未注册  a01eb0b55e40      已清除  a01eb0b55e40   ← 相同
已注册  03027b7198f6      再注册  03027b7198f6   ← 相同，且与上面不同
```

三态严格一致，**高亮确实被绘制**。所以不需要往主世界注入脚本、不需要事件桥，
`caretPositionFromPoint` 也在隔离世界里可用（命中判定要用它，不能用 Chrome 140 才有的
`highlightsFromPoint`——`minimum_chrome_version` 是 131）。
